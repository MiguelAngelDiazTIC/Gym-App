## Overall Impression

Today's work (P0s + accessibility + FAB + validation) shows: the detector is clean, cognitive load is low, and ConfirmDeleteButton is now an exemplary pattern reused consistently app-wide. But this re-run found a new crack of the same shape as what was just fixed — canceling an in-progress workout is still a single-tap destructive action, exactly what "The Two-Tap Delete Rule" is meant to prevent — and surfaced a deeper accessibility gap today's label pass didn't cover: nothing in the app is keyboard-reachable past the first screen.

## What's Working

1. ConfirmDeleteButton — exemplary execution: 44px hit boxes on every state, spatially distinct Cancel/Confirm, contextual aria-labels, the only delete path app-wide.
2. The new inline validation — uniform visual treatment (ring + caption) at every required field, without wiping the form.
3. getPreviousEntry() + the Fab relocation — both show real product thinking about the one-handed, mid-workout persona.

## Priority Issues

[P1] Canceling an in-progress workout loses all logged sets with a single, unconfirmed tap
- Why it matters: RoutineTab.tsx line 604, "Cancelar" calls setView('weekDetail') directly, discarding sessionLog instantly. Contradicts the app's own Two-Tap Delete Rule established today: a saved weight entry needs two taps to delete, an entire unsaved workout session needs zero.
- Fix: gate this exit behind a confirm step (reuse ConfirmDeleteButton's pattern) whenever sessionLog contains any sets.
- Suggested command: /impeccable harden

[P1] No keyboard-focus visibility; several primary navigation controls aren't real, focusable elements
- Why it matters: Button.tsx's shared base style sets outline:'none' on every variant with no :focus-visible replacement. ProfileScreen.tsx's profile-avatar tile and Card's onClick wrapper (week rows, exercise/meal disclosures) are plain motion.divs with onClick and no role/tabIndex/onKeyDown — a keyboard-only user cannot get past profile selection.
- Fix: add a visible focus-visible ring to shared button styles; convert onClick-bearing divs to real buttons or add role="button" + tabIndex={0} + Enter/Space handling.
- Suggested command: /impeccable harden

[P2] "One Voice Rule" (accent = one thing per screen) is violated on list-home screens
- Why it matters: every routine card gets its own gradient "Semanas · N" button, every day row its own gradient "Entrenar" pill, every nutrition day card its own coral flame + gradient bar — with several items, multiple coral-gradient elements sit on screen at once, contradicting DESIGN.md's own rule.
- Fix: drop repeated per-row actions to a glass/outlined treatment; reserve full gradient fill for a genuinely singular page-level action (the Fab already owns "add").
- Suggested command: /impeccable polish

[P2] Numeric input validation is inconsistent across screens
- Why it matters: WeightTab.addEntry rejects val<=0, but RoutineTab.addSet only checks isNaN (negative reps/weight silently accepted), and NutritionTab's macro fields coerce invalid input straight to 0 with no message, unlike weight/routine/exercise which now have proper inline errors.
- Fix: apply the same bounds-check + inline-error pattern to sets and macros.
- Suggested command: /impeccable harden

[P3] No celebratory/peak-moment feedback despite the design system reserving one
- Why it matters: theme.ts defines springMomentum explicitly "reserved for momentum-driven / celebratory moments" but it's never used anywhere. finishWorkout() just navigates back silently after the one moment that should feel rewarding.
- Fix: use springMomentum for a brief, restrained acknowledgment on finishWorkout.
- Suggested command: /impeccable delight

## Persona Red Flags

Sam (Accessibility-Dependent): cannot Tab to or activate the profile-avatar tiles — blocked at the very first screen without a mouse/touch. No visible focus ring anywhere even on real buttons. Week rows and disclosures are click-only.

Casey (Distracted Mobile User): the Fab is a real win for reachability, but the exact "interrupted mid-workout" scenario this persona embodies is handled worst: sessionLog lives only in React state during an active workout, never persisted — a backgrounded tab or a mis-tap on the unconfirmed "Cancelar" (P1 above) loses the entire session with no recovery.

Jordan (First-Timer / family member): a new routine shows "Semanas · 0" with no hint that a week must be added before "Entrenar" is reachable — an undocumented prerequisite with zero onboarding.

## Minor Observations

- BackButton is implemented twice nearly identically (RoutineTab.tsx and NutritionTab.tsx) — should be extracted to ui/.
- WeightTab's chart-type toggle uses raw glyphs "∿"/"▬" with no aria-label — a screen reader reads them literally.
- Modal's drag-handle pill visually implies drag-to-dismiss, but only tap-outside works.
- ConfirmDeleteButton's 4s auto-disarm has no visual countdown.
- ProfileScreen's 5-profile cap gives no advance warning before the "Add" tile disappears.

## Questions to Consider

- If losing a saved log requires two deliberate taps, why does losing an entire in-progress workout session require only one?
- The design system reserves a celebratory spring specifically for "momentum moments" — where does a user's actual effort ever get celebrated?
- If a family member with no technical background opens this cold, what currently tells them a "week" needs its own tap-through before they can train?

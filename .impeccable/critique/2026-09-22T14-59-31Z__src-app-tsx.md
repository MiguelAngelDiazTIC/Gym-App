The Spanish household-gym vocabulary, the weeks→days→exercises→sets nesting, and — the strongest evidence — the inline "previous week" reference while logging a new set (RoutineTab.tsx ~579-583) directly support progressive-overload training, a real feature no generic template would include. ## Overall Impression

The design system itself is well-built and consistently expressed — glass cards, restrained accent, spring motion. The real problem isn't visual, it's trust: nothing in the app confirms an action succeeded, prevents a destructive one, or explains a failure, and one specific flow (editing a workout log) actively destroys data before the user has agreed to anything. For a tool whose entire pitch is being a trustworthy personal record shared by a family, that's the single biggest opportunity.

## What's Working

1. Disciplined design-system execution in the common case — Card, PrimaryButton, SecondaryButton, Input correctly centralize the glass/pill/shadow vocabulary; Modal.tsx correctly portals to document.body and tracks keyboard inset instead of letting the keyboard cover a field.
2. The "previous week" inline reference in the workout-logging view is genuine product thinking built around real training behavior, not a generic CRUD form.
3. Disclosure's CSS-grid accordion is a smart, GPU-cheap alternative to JS-measured height animation, and correctly keeps tracking content that resizes while open.

## Priority Issues

[P0] Editing a past workout log destroys it before the user confirms anything
- Why it matters: The Pencil icon's onClick in RoutineTab.tsx (~line 527-537) calls deleteLog(log.id) synchronously, then opens the edit view. Tapping "Cancelar" afterward does not restore anything — the logged workout is permanently gone. Real data loss disguised as a normal edit.
- Fix: Don't delete until the edit is actually saved — keep the original log in state and only replace it inside finishWorkout(), or warn explicitly before deleting.
- Suggested command: /impeccable harden

[P0] Every destructive action app-wide is instant, unconfirmed, and paired with tiny touch targets
- Why it matters: Deleting a profile, routine, week, set, or meal item all cascade with zero confirmation, via a Trash2 icon rendered well under the 44×44 touch-target guideline — on a device this product explicitly expects to be used one-handed, mid-workout, and shared by a family.
- Fix: Add a confirm step (inline "tap again," or an undo toast with a 4-5s window) on any delete that cascades beyond the tapped item; bump icon-button hit area to ~44px regardless of visual icon size.
- Suggested command: /impeccable harden

[P1] No accessible labeling anywhere, and icon buttons default to a failing-contrast color
- Why it matters: Zero aria-label/alt/role attributes exist in src/. IconButton's default color (#57575f on #08080c) is ~2.8:1 contrast — below WCAG AA's 4.5:1 minimum — so delete/edit controls are hard to see even for sighted low-vision users, on top of being invisible to a screen reader.
- Fix: Add a required label prop to IconButton (single choke point, threads to every call site) that sets aria-label; bump default icon color to color.textSecondary (~7:1).
- Suggested command: /impeccable harden

[P1] Primary actions sit outside the thumb zone on every screen
- Why it matters: PRODUCT.md and DESIGN.md both frame this as one-handed, mid-workout phone use, yet every primary CTA ("Añadir", "Nueva", "Semana", "Añadir día") sits top-right in the header — the least reachable spot for a one-handed grip — while the reachable bottom is used for navigation only.
- Fix: Move the highest-frequency add flows (weight entry, set logging) to a bottom-anchored or FAB-style action.
- Suggested command: /impeccable layout

[P2] Silent validation failures give zero feedback
- Why it matters: addEntry(), addSet(), createRoutine(), addExercise(), createProfile() all guard invalid input with a bare if (...) return — the button appears to just do nothing. Exactly the profile this app is built for (family members, not just the power-user owner) has no way to learn what's wrong.
- Fix: Shake/error-color micro-interaction or a disabled-state on invalid input, so "nothing happened" reads as "invalid."
- Suggested command: /impeccable harden

## Persona Red Flags

Sam (Accessibility-Dependent): Every Trash2/Pencil/Check/X control has no accessible name at all; default icon color fails WCAG AA contrast; profile photos have no alt. High risk Sam can't safely use delete/edit controls.

Casey (Distracted Mobile User): Primary "Añadir"/"Nueva" buttons live outside one-handed thumb reach on an app documented as used one-handed mid-workout. Delete icons are ~20px targets with zero confirmation — a mis-tap while walking between sets permanently deletes data with no undo.

Jordan (Confused First-Timer): Tapping Pencil on a past log silently deletes it before any change is made — "Cancelar" doesn't undo the loss. Invalid input produces no message at all, so Jordan will assume the app is broken rather than that they mistyped something.

## Minor Observations

- The "Semanas · N" CTA (RoutineTab.tsx ~725) uses radius.md (16px) instead of radius.pill, directly contradicting DESIGN.md's pill-radius rule; the day-count selector and ProfileScreen's avatar tiles reintroduce hard 1px borders the "No Hard Edge Rule" forbids.
- springMomentum is defined in theme.ts specifically for celebratory moments (per its own comment) but is never used anywhere in src/ — finishing a workout, the app's actual peak moment, gets the same transition as everything else.
- Weight tab's "Variación" stat colors gains with the primary accent and losses with green — the accent then marks 3+ different things on one screen (primary action, chart line, gain indicator), diluting the system's own "One Voice" rule.
- ProfileScreen caps at 5 profiles with no messaging when the cap is hit — the "Añadir" tile just disappears.
- NutritionTab's "Añadir día" silently reopens today's existing day instead of creating a new one, with no indication that's what happened.

## Questions to Consider

- If a delete were never instant and always reversible for a few seconds, how many of this app's data-loss risks would simply disappear without a single confirmation dialog?
- The design system built a dedicated "celebratory" spring for exactly one moment, and the code never uses it — what would it look like to let the app feel proud of the user once, at the moment training math says it should?
- This is a shared family device. What currently stops one person from accidentally deleting another person's months of history?
